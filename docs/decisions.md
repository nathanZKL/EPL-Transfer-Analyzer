# Decisions

Significant choices for this project, why they were made, and what they cost. Newest first within each section. Add a row when a decision is made or changed; don't delete old ones, mark them **Replaced** and link the new one.

Source for the 2026-10-23 entries: the MVP plan agreed with Nathan that day ([mvp-plan.md](mvp-plan.md)) and the step 1 pull request (#1).

## Agreed

| # | Decision | Why | Tradeoff |
| --- | --- | --- | --- |
| D30 | **Efficiency stats need a minimum number of attempts before they get a percentile:** 25 plays for isolation, roll-man and putback points per play; 50 pull-up attempts for pull-up FG% (`analysis.MIN_ATTEMPTS`). Below that the stat is treated as missing (D29). Rim defence has no minimum (every 500+ minute player has 32+). (2026-10-27, after PR #5 review and the real fetch) | On 1–2 attempts a player could top the league by luck. | 143–236 of 378 qualifying players have no percentile for each of these stats. |
| D29 | **Missing stats in role scores (was open question O9).** Play-type volume blanks (`pnr_bh_poss_per100`, `iso_poss_per100`) rank tied for last, because NBA.com only lists players with 10+ possessions of a type, so a blank is known to mean "fewer than 10"; every build re-checks that floor and stops if it no longer holds (`prepare.check_listing_floor`). Any other missing percentile is left out of that player's fit score and the other weights count for more. A player with none of a role's stats gets no score. (2026-10-27, Nathan: "prioritize not making any assumptions") | Nothing is invented: the only blanks ranked are ones NBA.com's own listing rule explains. Every qualifying player gets every role score (378 of 378 on real data). | A score built from fewer stats is less complete; the method page must say so. |
| D28 | **All NBA.com field names are confirmed** by Nathan's fetch (2026-10-26, 9 tables, 582 players). Rim defence within 6 ft uses `FGM_LT_06`/`FGA_LT_06`, not nba_api's listed `D_FGM`/`D_FGA`. Resolves O5. | Real data beats the published schema. | None. |
| D27 | **Role weights start as Claude's best guesses** and are tuned once real rankings exist. (2026-10-26, answers part of O3) | Gets the scores working without blocking on basketball judgement calls. | First rankings may look odd until tuned. |
| D26 | **Role recipes live in `config/roles.toml`, read with Python's built-in `tomllib`.** Resolves O6. (2026-10-26) | No new dependency; same editing experience as YAML. | TOML is slightly less familiar than YAML. |
| D25 | **Players need 500+ minutes to get percentiles** (`analysis.MIN_MINUTES`). Resolves O4. (2026-10-26) | Small samples make rates jump around. | Short-season or late-signed players aren't ranked. |
| D24 | **Step 4 is split into 4a (extra NBA.com tables, per-100 stats, percentiles) and 4b (roles, fit and value scores)**, one PR each. The "Done when" table in the plan is confirmed. (2026-10-26) | Keeps each PR small, and 4a shows the real data before scores are tuned. | One more PR to review. |
| D23 | **Salary inputs are stricter.** `salary_usd` must be plain digits (Excel's `5.52E+07` would read back rounded), and an override that fits no salary row stops the import (adds to D19). (2026-10-26, PR #3 review fixes agreed by Nathan) | A wrong salary or a silently ignored override would break "never invent salaries". | Values like `12500000.0` must be cleaned by hand; deleting a salary row means deleting its override too. |
| D22 | **Players with no 2025-26 games stay unmatched, and the import says so.** NBA.com's stats table only lists players with at least one game, so e.g. Tyrese Haliburton (missed the season) can't get an ID. The unmatched message and README say to leave such rows alone, never override. Fetching NBA.com's full player list is in "Ideas for later". (2026-10-26, agreed by Nathan) | Keeps step 3 small; a player with no games can't get a fit score anyway. | He shows as unmatched on every import, and "didn't play" and "typo" share one message. |
| D21 | **Unmatched salary rows are reported, not fatal.** The import prints them and writes `data/processed/salary_unmatched.csv` with up to three suggested players (Python's built-in `difflib`). Players without a salary stay missing. Two salary rows that match one player stop the import. (2026-10-24, step 3 plan approved by Nathan) | A few odd names shouldn't block everything, and nothing is guessed. | Nathan has to read the report after each import. |
| D20 | **Real salary files live in `data/salaries/`** (`salaries_2025-26.csv`, `overrides.csv`), which is git-ignored. (2026-10-24, step 3) | Real data is never committed (D8); one obvious folder for hand-made files. | The files exist only on Nathan's machine, so he must back them up himself. |
| D19 | **Override file** `data/salaries/overrides.csv` with `player_name, team, player_id, note`. An override always beats the automatic match; an unknown `player_id` stops the import. (2026-10-24, step 3) | Fixes nicknames and other names the rule can't match. | Manual upkeep for each odd name. |
| D18 | **Salaries match players by normalised name; the team only breaks ties.** Normalising removes accents, case, punctuation and Jr./Sr./II–V. If the team can't settle a shared name, the row is unmatched. Resolves O2. (2026-10-24, step 3) | Traded players and different team codes (GS vs GSW) would break a name + team rule. | Nicknames (Nic vs Nicolas) need an override. |
| D17 | **Mock players use exactly the real table's columns** (`prepare.PLAYER_COLUMNS`), enforced by a test. Listed position was dropped from mock data. Resolves O8. (2026-10-24) | Analysis code and tests written against mock data work unchanged on real data. | The mock numbers had to be extended by hand; position is gone until a real source for it is added. |
| D16 | **Set up Python with `uv`** (`uv venv --python 3.13`). Resolves O7. (2026-10-24) | The Mac's default `python3` is 3.9.6; `uv` was already installed and fetches 3.13 itself. | One more tool to learn; plain `pip` still works inside the venv. |
| D15 | **NBA.com column names live only in `nbavalue/prepare.py`'s mappings**; everything downstream uses our own snake_case names. Step 2 fetches only the base and advanced tables, pausing 3 seconds between requests and reusing the newest saved snapshot unless `--refresh`. (2026-10-24, step 2 plan approved by Nathan) | A renamed NBA.com field is a one-line fix; fewer requests while field names are unconfirmed. | Hustle, tracking and play-type stats wait for a follow-up. The 3-second pause is a guess; NBA.com publishes no limits. |
| D1 | **The MVP answers one question:** which players best fit a role, and who gives the most of it per dollar. Trades, salary-cap rules, team needs and hosting are out. (2026-10-23) | Keeps the first version small enough to finish and explain. | The repo name and README pitch ("trade analyzer") promise more than v1 does. |
| D2 | **Local Streamlit app only, no hosted site.** (2026-10-23) | NBA.com terms allow personal, non-commercial use and forbid public republishing. | It can't be shared as a live link; the public portfolio shows code and mock-data screenshots. |
| D3 | **Stats come from NBA.com via `nba_api`, 2025-26 season.** (2026-10-23) | Rich stats (hustle, tracking, play types) that can measure roles directly. 2026-27 had barely started. | `nba_api` is unofficial and has no published rate limits; fetches must be cached and slow. Data is a season old. |
| D4 | **No Basketball-Reference.** (2026-10-23) | Its data-use policy forbids tools built on scraped data and using content to prompt AI. | Loses an easy, familiar source. |
| D5 | **Salaries come from a CSV, with a source, URL and date on every row, labelled `Reported salary`.** An optional scraper may fill it later. (2026-10-23) | Salaries are public facts, but the salary sites' terms for bulk use are unclear. | Building or updating the CSV can be manual work. |
| D6 | **Every value carries a label:** `NBA.com`, `Reported salary`, `Estimate` or `Mock` (`nbavalue/labels.py`). Fit and value scores are labelled as our own estimates. (2026-10-23) | Never mislead a reader about where a number came from. | Every table needs a label column and validation. |
| D7 | **Mock data is obviously fictional** (`Mock ` names, fake team codes, season `MOCK`) and enforced by tests. (2026-10-23) | Lets tests, offline demos and public screenshots run without republishing real data. | Mock columns are a first draft and must be updated once real NBA.com fields are confirmed. |
| D8 | **Real data is never committed.** `data/raw/` and `data/processed/` are git-ignored. (2026-10-23) | NBA.com terms. | Anyone cloning the repo must run the fetch themselves. |
| D9 | **Roles are not tied to positions; percentiles are league-wide** with a minimum-minutes cut. (2026-10-23) | NBA positions (G, F, C) are loose. | A guard and a centre are compared on the same scale for every role. |
| D10 | **Value score = role-fit percentile minus salary percentile.** (2026-10-23) | Simple and easy to explain to a fan. | Ignores contract length and cap context. |
| D11 | **Steps hand each other plain CSV files.** No database, backend, scheduler, Docker or extra cache layer. (2026-10-23) | About 500 players fit easily in pandas; fewer moving parts for a beginner. | No history or querying beyond what pandas does; files must be rebuilt by hand. |
| D12 | **Stack:** Python 3.11+, pandas, Streamlit, pytest, ruff. Dependencies in `requirements*.txt`, tool settings in `pyproject.toml`, no packaging. (2026-10-23) | Common, beginner-friendly tools. | `StrEnum` in `labels.py` needs 3.11+; older interpreters fail at import. |
| D13 | **Analysis logic lives in `nbavalue/` as plain functions; `app.py` only displays.** (2026-10-23) | Logic can be tested without the UI. | Slightly more files than one script. |
| D14 | **Six build steps, one small pull request each.** (2026-10-23) | Reviewable, learnable chunks. | Slower to reach a usable app with real data. |
